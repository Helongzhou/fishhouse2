# Real Unity acceptance

The scripts in this directory prepare and retain real-editor evidence. Preparing them is not a passing test. Run only in the exclusive time slot assigned by the coordinating agent, after the installer confirms that the same project is not open elsewhere.

The original `unity` project preserves Unity **2022.3.62f3** / URP **14.0.11**. A separate `unity6-validation` candidate can target the supported editor installed normally through Hub. The launcher and C# checks read the exact expected editor and URP versions from the selected project's `ProjectSettings/ProjectVersion.txt` and `Packages/manifest.json`; they require the actual editor/package to match those pins. Changing environments does not silently loosen version checks. The editor validation assembly references actual Core, adapter, editor setup and URP assemblies. No substitute Unity API or .NET-only adapter compilation is used.

From the repository root, after the runtime/localization Resources exports are current:

```sh
python3 verification/unity/run_acceptance.py --editor /Applications/Unity/Hub/Editor/2022.3.62f3/Unity.app/Contents/MacOS/Unity --mode batch --run-id agreed-batch-01
python3 verification/unity/run_acceptance.py --editor /Applications/Unity/Hub/Editor/6000.6.8f1/Unity.app/Contents/MacOS/Unity --project unity6-validation --mode batch --run-id agreed-batch-01
python3 verification/unity/run_acceptance.py --editor /Applications/Unity/Hub/Editor/6000.6.8f1/Unity.app/Contents/MacOS/Unity --project unity6-validation --mode play --run-id agreed-play-01
```

`--project` defaults to the original `unity` directory and accepts an explicit project path. Examples are prepared commands, not permission to launch outside the assigned run slot or evidence that either editor is ready. The launcher refuses to overwrite evidence and checks process inventory for the same project before launch. Evidence is separated under `verification/unity/<project-directory-name>/<run-id>/`. Each run records the exact command, selected project, expected versions, source hashes, timestamps, process exit, full editor log, stdout and the editor's JSON result. A successful process without a passing result file is a failure. Editor import or compilation failures can prevent the C# entry point from running; those remain visible in the raw editor log and invocation status.

`RunBatch` executes actual `AquariumProjectSetup.Prepare`, imports the scene and verifies script references, build-scene registration, URP version/pipelines and opaque/transparent material assets. Real `JsonUtility` must roundtrip a fresh save with no checkpoint and a stocked save with a populated checkpoint, active food bindings and owned ingested reserves. The prescribed route starts empty, builds only purchased scenery, runs the real nonzero nitrogen challenge and stocked observation, then verifies 8 Ember/8 Neon/6 shrimp and 280 coins. It also checks paused commands/clocks, deterministic continued state, free retry, actual host-file backup recovery and the runtime en/zh-CN scalar UI catalogs.

`RunPlaySmoke` enters the real scene in Play, survives domain reload, exercises actual entry `Awake`/runtime frames and the production route, then calls the real adapter `AdvanceSimulation(0.5)` versus fifteen `AdvanceSimulation(1/30)` calls from the same Unity-serialized state. It verifies the real animal bodies/camera/substrate collider and captures engine Error/Assert/Exception callbacks. It uses Editor-only reflection to observe the entry's private session and to arrange a shared starting snapshot; it adds no player-facing test API and copies no gameplay logic.

The Play entry first remains in Edit Mode until an initial editor `delayCall` completes and compilation/import are idle. For Unity 6 it also observes the normally created `UserSettings/Search.index` and the loaded default Search database's `ready`, `updating` and `LoadingState` through read-only reflection, because that editor type is internal. Two consecutive idle updates with `ready && !updating` allow the Play request. Missing observed properties, any captured startup error or the overall 180-second deadline fails the run. Phase, original deadline and complete captured report persist across assembly reload; startup state changes and the actual index path remain in `startupObservations`. The driver neither invokes Search initialization nor changes Search settings. This corrects the immediate-Play lifecycle used in retained failed runs `unity6-play-01/02`. The authorized real-editor `unity6-play-03` passed all 19 checks with exit 0 and no captured errors: it observed the default database Loading at 3.047 seconds and Complete/ready/not-updating at 13.351 seconds before entering Play. Its known batch-focus warning preserves the physical-input acceptance boundary.

Real runs `unity6-batch-02/03` observed Unity JsonUtility changing seven plant-position doubles by one ULP (maximum 2.78e-17 metres) while restoring a populated checkpoint. The resulting codec acceptance contract requires identical serialized field sets/structure/array order and strictly typed strings, IDs, booleans, enums, integer quantities, RNG state, coins, transactions and stages. Every continuous `double` must be finite and satisfy `abs(a-b) <= 1e-12 * max(1, abs(a), abs(b))`. The test-only reader retains raw number lexemes until the declared snapshot field type is known; it never converts integer identity into a generic double. Each nonzero double difference, its path, bound and maximum error is recorded in the report. Missing fields or invalid present substrate still fail. This is an observed numeric codec boundary, **not a promise of bitwise lossless saving**. Exact pause invariance and exact same-initial-state frame-chunk equivalence remain exact because those checks do not cross a codec. Earlier failed reports remain intact.

The prepared layout is a fixture matching the existing geometric teaching template, not a second implementation of the command rules. All placement, economy, ecology, save validation and progress decisions run through production classes. Feeding uses actual animal positions and actual consumption to establish reserves; it never fabricates nitrogen evidence or marks a gate complete.

These checks do **not** certify physical mouse/keyboard input, aesthetic quality, fish/shrimp hardscape navigation, font glyphs/layout, camera collisions, audio, GPU/performance, Windows player/offline operation, Steam or release research. Batch graphics and human visual/input acceptance are separate. Error-free logs alone cannot establish that every screen was drawn.

## Selected-source regression

After real-editor fixes, the old root `verify_slice.py` still targets the original `unity` Core. Use the following to run the existing pure C# checks against the **selected candidate's actual sources**:

```sh
python3 verification/unity/run_source_regressions.py --project unity6-validation --run-id agreed-source-regression-01
```

This generates isolated csproj/obj/bin directories inside that evidence run, builds the selected Core as C#7.3/netstandard2.1, and links the unchanged original behavior/ecology/gameplay/compatibility/integration `Program.cs` files against that same selected Core and its plain C# `DemoLocalization`. It never compiles a fake Unity adapter. Staging symlinks make the existing resource discovery resolve `Assets`/`unity` to the selected project and `data` to the authoritative shared data; all resolved targets, linked source hashes, commands, logs and exit codes are recorded. No original assertion, business code, resource file or original build directory is patched. Source changes during the run fail the result.

`unity6-source-regression-01` passed the Core build and 474 selected-source checks: behavior 49, compatibility 42, ecology 287, gameplay 47 and integration 49. Its report records no source changes during the run. Separate checks from older evidence directories are not included in that total.
